## Symptom

Every scheduled skill in the window failed with the same error signature recorded
in `memory/cron-state.json`:

```
"...","total_cost_usd":0,"usage":{"input_tokens":0,"cache_creation_input_tokens":0,
"cache_read_input_tokens":0,"output_tokens":0,...}
```

`scripts/skill-runs --hours 168` reported 899/912 failures (~0.9% success rate).
33 of 38 tracked skills hit >100 consecutive failures.

## Evidence

- Failed run `27856646818` (self-review, 2026-06-20T01:52Z) — env shows
  `CLAUDE_CODE_OAUTH_TOKEN:` (blank).
- Succeeded run `27862412997` (gitlawb-fleet-metrics, 2026-06-20T06:07Z) — env shows
  `CLAUDE_CODE_OAUTH_TOKEN: ***` (set, masked). 1858 output tokens, 36s duration.

## Why we didn't notice for two weeks

Every monitoring skill (`skill-health`, `heartbeat`, `batch-health`, `skill-evals`,
`skill-repair`, `memory-flush`) was itself failing for the same reason. The
monitoring path shared the broken dependency with the monitored path.

## Recommendations

1. **Credential canary** in `aeon.yml` (pre-flight check) that exits with a distinct
   error message when both `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` are
   empty. Saves ~1 min of wasted CI per failure and produces a clear signal.
2. **Out-of-band reliability monitor** — a tiny pinger (different account / status
   page heartbeat) that alerts when zero Aeon skills succeeded in the last 6h.
   This is the only way to detect a total-auth outage.
3. **Move to resolved** once 3 consecutive days of healthy runs are confirmed
   and clear `last_error` / `consecutive_failures` for affected skills.

## Recurrence — 2026-09-20

While investigating ISS-006 (cron scheduling) it became clear the two problems were
compounding: some of what looked like missed cron dispatches were actually skills
that *did* dispatch but immediately failed on auth. Pulled real job logs (not
cron-state inference this time) to confirm directly.

**Evidence — `planner` (job 106001616554, run 35482097855, 2026-09-20T01:42:54Z):**
```
env:
  ANTHROPIC_API_KEY: 
  CLAUDE_CODE_OAUTH_TOKEN: 
  BANKR_LLM_KEY: 
...
Using model: claude-opus-4-7
Gateway: direct
##[notice]Using direct Anthropic API
##[error]Claude CLI failed (truncated): ...
##[error]Process completed with exit code 1.
```
Job duration for the `Run` step: <1s (01:42:54 → 01:42:55) — matches the original
2026-06 signature (auth rejected before any API call, not a timeout).

**Evidence — `skill-repair` (job 106001735101, run 35482143097, 2026-09-20T01:43:58Z):**
identical env block, identical <1s failure. skill-repair was reactively dispatched
by `messages.yml`'s tick job because `planner` had **19 consecutive failures**
(`Reactive trigger: skill-repair (planner has 19 consecutive failures >= 3)`) — i.e.
the repair skill meant to fix this is hitting the exact same wall as everything else.

Onset dates vary by skill because each has a different cadence and the
`consecutive_failures` counter only started climbing once each skill's own dispatch
schedule crossed the outage window — but every one of these has been failing on
every single dispatch since. `skill-repair` (the mechanism meant to self-heal this)
and `heartbeat`/`batch-health`/`skill-health` (the mechanisms meant to detect it)
are themselves on this list — same blind spot as the original 2026-06 incident
("Why we didn't notice for two weeks" applies again here).

**This also explains part of what looked like ISS-006's "unresolved" day-1
validation**: `messages.yml`'s own tick job (the scheduler) is unaffected — it's a
plain bash/gh-cli job, not a Claude Code invocation — so the per-slot-cron fix in
PR #3 may be doing its job at the dispatch level. But every *dispatched* skill run
then dies in <1s on this auth wall, which reads identically to "never fired" in
`memory/cron-state.json` and in casual GitHub Actions run-list scans. ISS-006 and
this recurrence need to be evaluated independently once this is fixed.

**This cannot be fixed via a PR.** `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN`
is a GitHub Actions repository secret — only the repo owner (via Settings →
Secrets and variables → Actions) can restore it. Flagged directly to the operator;
no code change can resolve this issue.

Status kept at `investigating` (unchanged) — this was never `resolved`, so there's
no incorrect status to revert here, unlike ISS-006. Severity unchanged at
`critical`. Recommendation #1 (credential canary) and #2 (out-of-band monitor)
from the original filing remain unimplemented and would have caught this
recurrence in hours instead of weeks — still the right next step once auth is
restored.
